# `attachments` table guide — for the chargesheet extraction service

## Who this is for

The chargesheet extraction service (a separate repo/deployment — currently
`CHARGE_SHEET_INGEST_URL_PROD`, an Azure App Service reached via
`POST /chargesheet/ingest {blob_path}`) shares this repo's Postgres database
and writes directly into `"EDI_Tebra".attachments` (Drizzle model:
`claimAttachments` in `server/src/db/new_schema.ts`, lines 1099–1160). It is
not the only writer — Document Management's own upload endpoints
(`documentManagementRouter.ts`, `documentmangementrouterv2.ts`) insert the
**parent** "Paper Charge Sheet" row before ever calling ingest — but it's the
only writer of the **child** rows one parent splits into, and of the
extraction results on both.

This doc describes the table as it stands today, including several columns
and conventions added recently in this repo, so the ingest service's insert/
update paths can be brought in line with them. Nothing here changes the
ingest HTTP contract (`blob_path` in, extraction JSON out) — this is purely
about what the ingest service writes straight into the shared table.

## How the pieces fit together today

1. A user uploads a PDF via Document Management. This repo inserts **one
   parent row** (`attachment_type = 'Paper Charge Sheet'`, `parent_attachment_id
   IS NULL`, `status = 'T'`) and uploads the blob to
   `.../Exchange/Documents/Claim files/...`.
2. This repo calls the ingest API with that parent's `clm_att_path`.
3. The ingest service downloads the blob, splits it into per-claim pages,
   and — this is the part that lives in your repo — **inserts one child row
   per split page** (`parent_attachment_id` = the parent's `id`), writing
   the OCR/extraction results onto the relevant row(s).
4. This repo's own downstream code (`createClaimsFromProcessedDocumentAttachments.ts`,
   `professionalClaimCreationHelper.ts`) later reads `processed_extracted_data`/
   `raw_extracted_data` off the children, creates `claim_header` rows from
   them, and writes `type_id` (→ the new claim's id) /
   `associated_claim_dcn` / `claim_creation_response` back onto each child.
   **Your service should never set those three** — they belong to this
   repo's claim-creation step, which runs strictly after yours.

## Full column reference

| Column | Type | Notes |
|---|---|---|
| `id` | serial PK | — |
| `document_dcn` | varchar(100) | **Auto-generated by a `BEFORE INSERT` trigger** (`fn_generate_document_dcn_trigger`, migration `00110`). Do not set it — leave it out of your INSERT entirely. If you ever retry a failed insert with the same row object, make sure `document_dcn` isn't already populated from a prior attempt, since the trigger only fills it in when it's `NULL`. |
| `associated_claim_dcn` | varchar(100) | Set later, by this repo's claim-creation step. Leave `NULL` on insert. |
| `claim_creation_response` | jsonb | Same — this repo only, after a claim is created/fails. Leave `NULL`. |
| `parent_attachment_id` | integer | For a child row: the parent "Paper Charge Sheet" row's `id`. `NULL` on the parent itself. |
| `parent_attachment_name` | text | The parent's `original_file_name`, denormalized onto the child for display. Set it when you set `parent_attachment_id`. |
| `original_file_name` | text | Human-facing file name. |
| `retrieval` | text | Set to `"API"` by the existing upload path; not something your service needs to touch on children unless you want to be explicit. |
| `upload_source` | text | Free-text provenance tag (other flows use values like `'practice_fusion'`; Document Management's own uploads don't set it). Not currently used by the chargesheet path — leave as-is unless you want a tag identifying your service as the writer. |
| `rotation_degrees` | integer, default `0` | Page rotation applied/needed. |
| `page_count` | integer | Set on the row the count applies to (typically the parent, once known). |
| `extracted_files_count` | integer | How many child rows this parent produced. |
| `client_id` / `group_id` / `practice_id` | integer, FK | Copy straight from the parent row — same client/group/practice for every child. |
| `processed` | boolean, default `false`, **NOT NULL** | Flip to `true` once `processed_extracted_data` is written for that row. Downstream code (and the dashboard) treats `processed=false` as "still being worked on." |
| `sha` | varchar(64) | SHA-256 of the file content, hex. Set by the initial upload for the parent; not required on children unless you want per-page integrity checks. |
| `clm_att_path` | text | **Must be a bare Azure blob path, never a full URL.** See the dedicated section below — this is the single most important rule in this doc. |
| `clm_att_filename` | text | Blob's file name (just the name, not the path). |
| `clm_att_datetime` | timestamp | When the file was written to blob storage. |
| `clm_login` | varchar(500) | Who/what performed the write. Existing convention is a human name/login for user uploads, `'system'` for automated writers — use `'system'` (or a name identifying your service, e.g. `'chargesheet-ingest'`) rather than leaving it `NULL`. |
| `status` | varchar(5), default `'G'`, **NOT NULL** | See status vocabulary below. |
| `attachment_type` | varchar(50) | **Must exactly match `"Paper Charge Sheet"` (Title Case)** for every child of a Paper Charge Sheet parent — see the casing section below. Several places in this repo do a case-sensitive `=` comparison against that exact string, not a case-insensitive one. |
| `raw_extracted_data` | jsonb | Raw OCR/AI output. This repo's own read code expects a shape roughly like `{ pages: [{ procedure_codes: [...], circled_diagnoses: [...], ... }], source_pdf: "..." }` (see `buildProcessedExtractedData` in `documentManagementRouter.ts` for the exact shape it currently reads) — keep it compatible if you change what you emit here. |
| `processed_extracted_data` | jsonb | Normalized/derived extraction result this repo's claim-creation step consumes directly. |
| `extraction_metadata` | jsonb | Free-form metadata about the extraction run itself (confidence, model version, timing, etc. — not read by any downstream logic in this repo today, so its shape is entirely up to you). |
| `user_id` | uuid | Set to the uploading user's id on the parent; for a system-generated child row, either mirror the parent's `user_id` or leave `NULL` — both already occur elsewhere in this codebase for automated writers. |
| `assigned_to_id` | uuid, FK → `users.id` | Who the document is queued to in Document Management. Not something the ingest service should set — leave `NULL` on new children (the existing upload path assigns the parent to the uploader; children are picked up separately). |
| `category` | varchar(20), nullable | **New. See the dedicated section below — please start setting this.** |
| `is_archived` | boolean, nullable | **New. See the dedicated section below — please start setting this.** |
| `created_at` / `updated_at` | timestamp, **NOT NULL, no DB default** | You must supply both explicitly on every insert (and bump `updated_at` on every update) — the column has no `DEFAULT now()`, so an insert that omits it will fail. |

Columns intentionally **not** in this list because they belong to a
different ingestion pipeline (Tebra/Practice Fusion/PF Facesheet's
"medical extraction → Facesheet" flow, unrelated to chargesheet processing)
and your service should never populate them: `type_id` (also
claim-creation-only, see above), `associated_patient_id`,
`associated_claim_id`, `ocr_text`, `rpa_appointment_id`, `retry_count`,
`sftp_file_path`, `json_manifest_entry`, `associated_patient_header_id`.

## Rule 1 — `clm_att_path` must be a bare blob path, never a full URL

Every read/write entry point in `azureBlobAttachmentManager.ts`
(`downloadFile`, `deleteFile`, `getPresignedDownloadUrl`, `archiveFile`,
`fileExists`) passes `clm_att_path` straight into the Azure SDK's
`getBlobClient(blobName)` / `getBlockBlobClient(blobName)`, which treats the
argument as a **literal blob name**, not something to parse as a URL. A row
whose `clm_att_path` is a full `https://<account>.blob.core.windows.net/<container>/<path>`
URL makes Azure look for a blob whose name is that entire URL string, and
every one of those operations fails with `The specified blob does not
exist.` — this exact bug hit ~1248 rows from an earlier, unrelated migration
into this table and had to be repaired with a one-time script. Store only
the path portion (e.g. `SomeClient-123/Exchange/Documents/Claim files/2026-09-02/file.pdf`),
never the scheme/host/container prefix.

## Rule 2 — `attachment_type` casing must match exactly

The canonical values, used verbatim (Title Case) everywhere in this repo,
are:

- `"Claim CSV File"`
- `"Paper Charge Sheet"`
- `"Facesheet"`
- `"Paper EOB"`

For chargesheet children, that means literally the string `"Paper Charge
Sheet"` — copy it from the parent row rather than hardcoding a differently-
cased variant. This matters because several places do an exact,
case-sensitive comparison against that string, not a case-insensitive one —
e.g. `eq(claimAttachments.attachmentType, "Paper Charge Sheet")` in
`resetUnarchivedChildAttachments.ts`, `createClaimsFromProcessedDocumentAttachments.ts`,
`archiveClaimedChildAttachments.ts`, `reconcileParentChargeSheets.ts`, and
more. A row written as `"paper charge sheet"` or `"PAPER_CHARGE_SHEET"`
would silently fall out of every one of those queries — it wouldn't error,
it would just be invisible to claim creation, archiving, and the reset/
reconciliation tooling. (One unrelated table in this same DB, `attachments`
itself historically, had exactly this class of bug with a `'facesheet'` vs
`'Facesheet'` mismatch — migration `00134` fixed it after the fact. Getting
the casing right at insert time avoids needing the same kind of cleanup
here.)

## Rule 3 (new) — populate `category` and `is_archived` going forward

These two columns were added in this repo (migration `00133`) so Document
Management's dashboard can filter by real DB columns instead of re-deriving
"is this a claims doc, and is it archived" from `clm_att_path` on every
request. They're nullable with **no default on purpose** — `NULL` currently
means "not backfilled / not yet set by this writer," and the dashboard's
query falls back to computing both from the path for any row where they're
`NULL`, so nothing breaks if they're left unset. But two writers in this
repo (the Tebra and Practice Fusion medical-extraction flows) already set
them explicitly on every insert, and the ask is for the chargesheet ingest
service to do the same, so its rows get the same DB-level filtering the
rest of the table is moving toward instead of perpetually relying on the
path-inference fallback.

**`category`** — `varchar(20)`, one of:
- `"claims"` — this is the value for every chargesheet row (parent and
  children alike). Chargesheet processing has no `"remittance"` case.

**`is_archived`** — `boolean`:
- `false` for every row you insert (a freshly-split child, or a parent at
  ingest time, is never archived yet).
- If your service is ever the one that moves a row's blob under an
  `Archive/...` prefix (today that's done later, by this repo, once a claim
  is created from the child — see `archiveClaimedChildAttachments.ts`), flip
  this to `true` in the same update that changes `clm_att_path` to the
  archived location. Otherwise, don't set it to `true` — leave it `false`
  and let this repo's archiving step do it.

Concretely, every child row you insert should include:

```json
{ "category": "claims", "is_archived": false }
```

## Status (`status`, varchar(5)) vocabulary

Free-form, but these are the values already in live use on this table —
reuse them rather than inventing new ones:

| Value | Meaning |
|---|---|
| `'T'` | Just uploaded, not yet processed. What a fresh parent row is created with. |
| `'G'` | General / ready for review (also the column default). |
| `'E'` | Exception — extraction failed or needs manual attention. Set this on a child row your service couldn't successfully extract, instead of silently omitting it or leaving it stuck at `'T'`. Existing reset/reconciliation tooling in this repo specifically looks for `status = 'E'` children to find rows needing a re-run. |
| `'C'` | Claimed — a claim has been created from this row. Set by this repo's claim-creation step, not by your service. |
| `'TR'` | Trashed. Not something your service should set. (Note: this used to be `'Z'` in older rows; `'Z'` is retired — don't reintroduce it, it collides with an unrelated, different meaning of `'Z'` on `claim_header.status`.) |

A reasonable default for a freshly-inserted, successfully-split child row is
`status: 'G'`; use `'E'` for one that failed extraction.

## Parent/child convention

- The parent "Paper Charge Sheet" row has `parent_attachment_id IS NULL`.
- Every child gets `parent_attachment_id` = the parent's `id`,
  `parent_attachment_name` = the parent's `original_file_name`, and the
  **same** `attachment_type`, `client_id`, `group_id`, `practice_id` as the
  parent.
- Nothing in this repo validates a child's `attachment_type` against its
  parent at write time — but several scripts (`resetChargesheetsFromScratch.ts`,
  `reconcileParentChargeSheets.ts`) defensively check it and skip/flag any
  parent whose children don't all match. Keep them matching to avoid rows
  quietly falling out of that tooling.

## Checklist for your insert/update paths

- [ ] `clm_att_path` is a bare blob path on every insert/update — never a full `https://...` URL.
- [ ] `attachment_type` is the exact literal `"Paper Charge Sheet"` (Title Case) on every child row.
- [ ] Don't set `document_dcn` — the DB trigger fills it in.
- [ ] Don't set `type_id`, `associated_claim_dcn`, or `claim_creation_response` — those are written later, by this repo's claim-creation step.
- [ ] Set `category: "claims"` and `is_archived: false` on every row you insert.
- [ ] Set `status: 'E'` on a child that failed extraction, instead of leaving it at a pre-processing status.
- [ ] Flip `processed: true` once `processed_extracted_data` is written for that row.
- [ ] Always supply `created_at` and `updated_at` explicitly (no DB default) and keep `updated_at` current on any later update to the same row.
